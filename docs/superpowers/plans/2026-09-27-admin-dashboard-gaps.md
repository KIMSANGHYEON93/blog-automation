# 관리자 대시보드 부족 기능 — 분할 구현 계획 (2026-09-27)

## 배경

대시보드(`src/interface/web/`)는 지금 **로그인 · 목록/필터 · 상세(본문) · 1건 발행 · 작업 상태**만 한다.
2026-09-23~26 네이버 글 3건을 내는 동안 관리자가 실제로 한 일 대부분은 대시보드 밖(스크립트, `docker exec`,
gspread 직접 수정)에서 했다. 그 목록이 곧 부족한 기능이다.

| 실제로 한 일 | 한 방법 | 기능 |
|---|---|---|
| 키워드 고르기(티스토리와 중복 확인) | 스크립트로 두 탭 조회 | F3 |
| 키워드 행 추가 | `add_keyword_row` 스크립트 | F3 |
| 글 생성 실행 | `docker exec n8n execute` | F4 |
| 본문 사실 오류 수정 | gspread로 P열 직접 수정 | F1 |
| 발행실패 → 발행대기 복구 | 스크립트로 `reset_failed_to_pending` | F1 |
| 발행 전 에디터 점검 | `naver_blog.py draft` | F2 |
| 발행 후 카테고리·태그·사진 확인 | Playwright로 공개 글 조회 | F6 |
| 첫 사진이 주제와 무관 | (미해결) | F5 |

## 원칙

- 기능 하나 = 커밋 묶음 하나. 순서대로 하고, 앞 기능이 끝나야 다음으로 간다.
- 각 기능은 **단위 테스트(RED→GREEN) + 라우트 테스트 + 실측 1회**로 끝낸다. 실측은 공개 발행 없이(임시저장·로컬) 가능한 것부터.
- 보안 규칙 유지: 모든 POST는 CSRF, 로그인 필요, 사용자 입력은 길이·형식 검증, 템플릿 이스케이프, CSP(JS 없음) 유지.
- 대시보드는 플랫폼(`--platform tistory|naver`)별 탭만 다룬다. 티스토리 자동 발행 흐름은 건드리지 않는다.

## F1. 게시물 편집과 상태 복구

**왜:** 감마 글의 틀린 크레딧 정보를 고치려고 시트를 직접 수정했다. 실패 글 복구도 스크립트로 했다.

- 상세 화면에 편집 폼: 제목, 카테고리, 태그, 본문(textarea). `발행대기`·`보류`·`발행실패` 상태에서만.
- 상태 버튼: `발행실패 → 발행대기`, `보류 → 발행대기`. 도메인 전이 규칙(`Post`)을 그대로 쓴다.
- 저장소: `PostRepository`에 `save_content(row_index, content)` 추가(시트는 제목·태그·본문·카테고리 열만 갱신).
- Use case: `EditPostUseCase` (본문 3000자 미만이면 저장은 하되 발행 불가 사유로 표시 — 기존 `publish_blockers` 재사용).
- 테스트: use case(허용/거부 상태, 전이), 라우트(CSRF·검증·XSS 이스케이프), InMemory 저장소.
- 실측: 네이버 탭 한 행을 대시보드에서 고치고 시트에서 확인.

## F2. 발행 전 미리보기와 임시저장 시험

**왜:** 번호 줄바꿈·사진 개수 문제는 공개 발행 후에 알았다.

- 상세 화면 "미리보기": `build_naver_html` 결과를 안전하게 렌더(허용 태그만 `bleach`로 정리, 사진 자리는 회색 상자 + 사진 설명).
- "임시저장 시험" 버튼: `draft_only=True`로 작업 실행 → 결과 화면에 붙여넣기 글자 수, 업로드된 사진 수, 경고 목록.
- 테스트: 미리보기 sanitize(스크립트·이벤트 속성 제거), 작업 실행기가 draft 결과를 표시.
- 실측: 발행대기 글 하나로 임시저장 시험.

## F3. 키워드 추천과 등록

**왜:** 다음 글 키워드를 사람이 떠올리고, 티스토리 190여 건과 겹치는지 스크립트로 확인했다.

- "키워드" 화면: 후보 목록 + 등록 버튼 + 직접 입력 폼.
- 후보 출처: AI-Brain 용어 탭(`--generate-term-keywords`와 같은 생성기) + 네이버 유형(사용법·비교·개념) 패턴.
- 필터: **두 탭(티스토리·네이버) 모두**와 중복 검사(n8n `Check Duplicate`와 같은 기준 75%), B2C 필터 재사용.
- 등록: `add_keyword_row`(상태 `대기`).
- 테스트: 후보 생성·중복 필터(기준 일치), 등록 라우트 검증(길이, 빈 값, 중복).
- 실측: 후보 3개 등록.

## F4. 생성 실행 버튼

**왜:** 글 생성은 n8n 02:00 스케줄 또는 `docker exec`뿐이다.

- 네이버 워크플로우에 Webhook 트리거 추가(`build_naver_workflow.py`가 생성, 공유 비밀값 헤더 검증).
- 대시보드 "지금 생성" 버튼 → `127.0.0.1:5678/webhook/...` 호출, 결과는 목록 새로고침으로 확인.
- 테스트: 생성 스크립트가 webhook 노드·비밀값 검사를 넣는지, 라우트가 비밀값을 화면에 노출하지 않는지.
- 실측: F3에서 등록한 키워드로 생성 1회.

## F5. 제목이 들어간 대표 썸네일

**왜:** 첫 사진이 주제와 무관한 그림(의자·화분)이었다. 대표 사진은 검색 결과 썸네일이 된다.

- `images.py`에 `title_thumbnail(title, background_bytes) -> bytes`: 생성 배경을 어둡게 깔고 제목을 한글 굵은 글꼴로 2~3줄 배치(Pillow). 글꼴은 저장소에 포함(라이선스 OFL, 예: Pretendard Bold).
- 어댑터: 첫 사진만 썸네일로, 소제목 사진은 지금처럼.
- 테스트: 줄바꿈(글자 수 기준 자동 줄나눔, 최대 3줄), 출력 크기·형식, 긴 제목 말줄임.
- 실측: 임시저장 시험(F2)으로 썸네일 확인 → 스크린샷 검토.

## F6. 발행 후 자동 점검

**왜:** 태그 6개/10개, 사진 6장 같은 문제를 사람이 공개 글을 열어 찾았다.

- 발행 직후 모바일 공개 글을 읽어 점검: 카테고리 일치, 태그 수, 사진 수(≤5), 인용구 수, 번호만 남은 줄 0.
- 결과를 작업 화면과 시트 오류 열(경고로)에 기록. 점검 실패가 발행 결과를 바꾸지는 않는다.
- 테스트: 점검 파서(저장한 HTML 조각으로), 경고 기록.
- 실측: 다음 공개 발행에 적용.

## F7. 발행 현황

- 목록 상단: 오늘 발행 수 / 일일 한도, 다음 발행 가능 시각, 최근 발행 5건 링크.
- 테스트: 쿼터 계산 표시.

## 순서와 이유

F1 → F2 → F3 → F4 → F5 → F6 → F7

- F1·F2는 이후 모든 기능의 **안전장치**(고치고, 공개 전에 본다).
- F3·F4가 되면 "키워드 3개 찾아 3건 작성"을 대시보드만으로 할 수 있다.
- F5는 F2의 임시저장 시험으로 검증한다.
- F6·F7은 운영 편의.

## 첫 번째 목표(키워드 찾아 3건 + 제목 썸네일)와의 관계

F3·F4·F5가 끝나면 대시보드에서 실행한다. 네이버 일일 한도가 1건이라 **3건 발행은 3일**에 걸친다
(생성·임시저장 점검은 하루에 모두 가능). 한도를 올릴지는 발행 시점에 따로 정한다.
