# 파이프라인 내구성: 로그인 가용성 + 키워드 공급

작성 2026-09-23. 모든 수치는 같은 날 `kimsanghyeon.tistory.com` 실측이다.

두 병목을 따로 다룬다.
- **병목 A** — 카카오 MFA가 뜨면 발행이 멈추고, 멈춘 사실을 아무도 모른다
- **병목 B** — 키워드 발굴이 0건이라 다음날 발행할 글이 없다 (해결 완료)

---

## 병목 A: MFA로 발행이 끊긴다

### 측정한 사실

**1) 평소에는 2FA가 안 뜬다. 쿠키가 살아 있으면 조용히 통과한다.**

`.browser_data/Default/Cookies` 실측:

| 쿠키 | 호스트 | 종류 | 만료 |
|------|--------|------|------|
| `_kau` | `.kakao.com` | 영속 | 364일 |
| `__T_`, `__T_SECURE` | `.kimsanghyeon.tistory.com` | **세션** | 브라우저 종료 시 소멸 |
| `TOP-XSRF-TOKEN` | `www.tistory.com` | **세션** | 브라우저 종료 시 소멸 |

티스토리 세션은 매 실행 새로 발급된다. 그런데 `kakao_auth.kakao_login()`이
`_kau` 덕에 OAuth 리다이렉트를 무인으로 통과해 세션을 다시 만든다 —
로그에 찍히는 `쿠키로 자동 로그인 성공`이 이 경로다.

**따라서 2FA는 `_kau`가 무효화될 때만 발생한다.**

**2) 정기 실행은 로그인을 거의 안 한다.**

로그 전수 집계:

| 작업 | 로그 수 | 브라우저 기동 |
|------|---------|---------------|
| publish | 10 | 5 |
| revise | 5 | 4 |
| check_index / submit_index / dashboard / recover_failed / discover_keywords | 35 | **0** |

브라우저를 여는 건 `publish`·`revise` 둘뿐이고, 그것도 처리할 글이 있을 때만이다.
정상 운영이면 하루 약 2회.

2026-09-22 밤 `_kau`가 무효화된 원인은 스케줄이 아니라 **1시간 안에 반복한 수동 로그인 8회**다.
카카오 이상탐지에 걸렸다.

**3) 진짜 문제는 2FA가 아니라 실패가 조용하다는 것이다.**

```python
# publish_posts.py:99, revise_posts.py:48, cli.py:174/450/531
if not browser.login():
    logger.error("로그인 실패 — 발행 중단")
    return          # ← 예외 없음
```

`return` → `main()` 정상 종료 → `run_pipeline_b.sh`의 `EXIT_CODE=0` → launchd는 성공으로 기록.

알림도 나가지 않는다. `_build_notification()`은 `SLACK_WEBHOOK_URL` /
`TELEGRAM_BOT_TOKEN`+`TELEGRAM_CHAT_ID`가 있어야 실제 어댑터를 만드는데
`.env`에 셋 다 없어 `NullAdapter`가 반환된다. 게다가 호출 지점이
`cli.py` 318·559·656행뿐이라 **로그인 실패 경로에는 알림 호출 자체가 없다.**

> 이 조합 때문에 파이프라인이 2026-05-06부터 09-21까지 약 4개월 반 동안
> `No module named src`로 전사했는데 아무도 몰랐다. 같은 구조가 그대로 남아 있다.

### 개발 방향

#### P0 — 실패를 시끄럽게 ✅ 완료 (a67a09a)

목표: 다시는 조용히 죽지 않는다. 2FA 자체보다 이게 먼저다.

1. `LoginFailedError`를 `src/domain/exceptions.py`에 추가하고,
   `browser.login()` 실패 시 `return` 대신 raise한다.
2. `cli.py`의 `_main_inner`가 이 예외를 잡아 알림을 보내고 **non-zero로 종료**한다.
   `run_pipeline_b.sh`가 그 코드를 그대로 넘기므로 launchd 상태에 드러난다.
3. `.env`에 알림 채널을 채운다. 텔레그램이 웹훅보다 설정이 짧다.

   ```
   TELEGRAM_BOT_TOKEN=...
   TELEGRAM_CHAT_ID=...
   ```

4. 테스트: `MockBrowserAdapter`가 `login()`에서 False를 반환할 때
   `PublishPostsUseCase.execute()`가 `LoginFailedError`를 올리는지.

**효과**: 로그인이 막히면 즉시 안다. 4개월 공백이 재발하지 않는다.

#### P1 — 2FA를 즉시 알린다 ✅ 완료 (61c4f5b)

지금은 `TWO_FA_WAIT_SEC = 120` 동안 말없이 기다리다 실패한다.
휴대폰이 옆에 있어도 승인할 기회가 없다.

1. `kakao_auth._enter_credentials_and_wait()`에서 `2단계 인증 감지` 시점에
   알림을 쏜다. Domain 의존을 피하려면 `NotificationPort`를 인자로 주입한다.
2. `TWO_FA_WAIT_SEC`을 120 → 300으로 올린다. 알림을 보고 승인할 시간을 준다.

**효과**: 2FA가 "발행 중단"에서 "몇 분 지연"으로 내려간다. 무인 승인은 불가능하지만
(카카오톡 푸시는 사람이 눌러야 한다) 사람이 개입할 수 있는 창을 만든다.

#### P2 — 로그인 빈도를 더 줄인다 (반나절)

`_kau` 무효화 위험은 로그인 횟수에 비례한다. 티스토리 세션을 디스크에 보존해
브라우저 로그인 자체를 줄인다.

1. 로그인 성공 직후 `sb.get_cookies()`에서 티스토리 도메인 쿠키를
   `.browser_data/tistory_session.json`으로 저장한다 (파일 권한 0600).
2. 다음 실행은 브라우저를 열고 쿠키를 주입한 뒤 `/manage` 접근으로 유효성만 확인한다.
   200이면 로그인 단계를 건너뛴다.
3. 무효면 그때만 정규 로그인 경로를 탄다.

**효과**: 로그인 2회/일 → 세션 수명당 1회. 수동 디버깅 시에도 재로그인을 안 하므로
어젯밤 같은 이상탐지 유발을 막는다.

#### P3 — 발행을 순수 HTTP로 (1~2일, 선택)

발행 경로에서 브라우저가 하는 일은 이미 거의 없다.

| 작업 | 구현 | 브라우저 필요? |
|------|------|----------------|
| 발행 | `POST /manage/post.json` | 쿠키만 |
| 수정 | `PUT /manage/post/<id>.json` | 쿠키만 |
| 삭제 | `DELETE /manage/post/<id>.json` | 쿠키만 |
| 카테고리 | `GET /manage/category.json` | 쿠키만 |

P2의 쿠키 저장이 있으면 `requests.Session`으로 전부 대체된다.
`BrowserPort` 옆에 `TistoryApiPort`를 두고 어댑터를 하나 더 만드는 구조다.

**효과**:
- 실행 시간이 글당 2분대 → 초 단위로 줄어든다
- `script timeout`이 사라진다. 2026-09-22 539번 중복 발행의 직접 원인이었다
- launchd 환경에서 Chrome 프로세스 누수·권한 문제가 없어진다

브라우저는 로그인 때만 남는다.

### 우선순위 정리

| 단계 | 비용 | 효과 | 상태 |
|------|------|------|------|
| P0 실패 알림 + 종료코드 | 반나절 | 가장 큼 — 침묵 제거 | ✅ `a67a09a` |
| P1 2FA 즉시 알림 | 1~2h | 큼 — 중단을 지연으로 | ✅ `61c4f5b` |
| P2 세션 재사용 | 반나절 | 중 — 재발 확률 감소 | 대기 |
| P3 순수 HTTP 발행 | 1~2일 | 중 — 속도·안정성 | 대기 |

**P0·P1 실증** (로그인을 강제 실패시켜 측정):

```
[알림] WARNING: 카카오 2단계 인증 필요 — 카카오톡에서 승인해 주세요 (최대 300초 대기)
[알림] ERROR:   Pipeline B 크래시: LoginFailedError: Tistory 로그인 실패 — ...
종료코드=1
```

`run_pipeline_b.sh`가 이 코드를 그대로 넘기므로 launchd 상태에 드러난다.

> **남은 전제**: `.env`에 `TELEGRAM_BOT_TOKEN`+`TELEGRAM_CHAT_ID`(또는
> `SLACK_WEBHOOK_URL`)가 없으면 `NullAdapter`가 반환돼 알림이 아무 데도 안 간다.
> 종료코드는 이미 동작하므로 launchd 상태로는 보이지만, 즉시 알림을 받으려면
> 채널 설정이 필요하다. P0·P1의 가치는 이 한 줄에 달려 있다.

## 병목 B: 키워드 공급 (해결 완료)

### 측정한 사실

`DiscoverKeywordsUseCase.execute()`의 `days` 기본값이 28이었고
`cli.py`가 이 값을 넘기지 않아 항상 28일 창으로 조회했다.

같은 사이트·같은 필터, 창 길이만 바꾼 실측:

| 조회 기간 | GSC 반환 | 노출 분포 (0-1 / 2-4 / 5-9 / 10-29 / 30+) | 노출≥5 통과 |
|-----------|----------|---------------------------------------------|-------------|
| 28일 | 500 | 230 / 132 / 56 / 48 / 34 | **0건** |
| 90일 | 500 | 157 / 111 / 56 / 77 / 99 | **10건** |

저트래픽 블로그에서 28일 창은 쿼리별 노출을 흩어놓아 `min_impressions=5`를
아무도 넘지 못하게 만든다. 90일은 같은 쿼리의 노출을 누적해 임계치를 넘긴다.

발굴 0건 → Pipeline A가 생성할 키워드 없음 → 다음날 발행 0건. 공급이 통째로 끊긴다.

### 조치

`DEFAULT_LOOKBACK_DAYS = 90`, CLI에 `--discover-days` 노출,
`cli.py`에 `from __future__ import annotations` 추가(3.9 타깃 `X | None` 대응).

검증: 발굴 0건 → 10건. 상위 키워드는 `클로드 크레딧 충전`(노출 49),
`클로드 추가 사용량 가격`(15), `클로드 크레딧 받기`(14) — B2B AI 주제로 적합하다.
3건을 `대기`로 등록해 Pipeline A가 생성하도록 했다.

### 남은 구조적 한계

GSC는 **이미 노출된 쿼리만** 반환한다. 신규 주제는 발굴 대상에 아예 없다.

```
트래픽 없음 → GSC 쿼리 적음 → 신규 키워드 없음 → 신규 글 없음 → 트래픽 없음
```

90일 창은 이 루프를 늦출 뿐 끊지 못한다. 90일치도 소진되면 다시 0이 된다.
끊으려면 GSC 밖의 시드가 필요하다.

**후속 방향** (필요해지면):

1. **관측 먼저** — 발굴 건수를 시트나 대시보드에 기록한다.
   0건이 며칠 연속이면 알림. 지금은 0건이어도 exit 0이라 또 조용하다.
2. **게이트 재검토** — 현재 필터 탈락은 노출<5가 268건, CTR≥10%가 110건이다.
   CTR 게이트는 "이미 잘 먹히는 키워드 제외"가 목적인데 110건은 과하다.
   `max_ctr`을 0.15~0.20으로 올리는 게 `min_impressions`를 내리는 것보다 안전하다.
3. **외부 시드** — 이미 붙어 있는 AI-Brain 볼트(`AI브레인용어` 탭 381건)가
   GSC와 무관한 B2B 주제원이다. 용어 카드에서 직접 키워드를 뽑는 경로를 열면
   트래픽 의존 루프를 벗어난다. `scripts/sync_brain_terms.py`가 이미 데이터를 넣고 있다.
